The problem behind the request

Stated Problem
A software vendor already uses ECS and needs to choose how to run its containers as the service grows.
Actual Problem
The client needs to choose the right ECS compute model as the service grows. The solution must balance cost, scalability, availability, and operational effort.
Business Impact
A poor choice could increase cloud costs, create more work for a small engineering team, or make it harder to maintain 99.9% availability as demand grows.
Symptoms
Twelve container tasks run continuously, and demand doubles for two hours each weekday. CPU usage is mostly steady. The nightly worker needs a special host setup, while the API does not.
Constraints
Only two platform engineers maintain the service. The architecture must support 99.9% availability. Costs must be compared over a full month, including idle capacity, operations, data transfer, and resilience. The nightly worker also needs a special host configuration.
Uncertainties
We do not know the exact cost of each option, how much time the engineers spend managing infrastructure, or the exact host requirements of the nightly worker. These points could change the final recommendation.

Architecture options

OPTION 1 · 268c42ca-938e-4338-af85-d1eb58c2e269

ECS on EC2 for all workloads

Summary
Run the API and nightly worker on ECS using EC2 instances. Use Auto Scaling to add capacity when demand increases.
Components
ECS runs the containers on EC2 instances. The API runs as an ECS service behind a load balancer. An Auto Scaling Group provides EC2 capacity and adds instances when needed. The nightly worker runs on EC2 hosts that support its special configuration.
Advantages
Lower compute cost can be possible for steady workloads. Full control over the EC2 hosts. Supports the special host requirements of the nightly worker.
Disadvantages
The team must manage EC2 capacity, patching and scaling. Idle EC2 capacity may still cost money. More operational work for a team of only two engineers.
Cost
Compute cost may be lower for the steady 24/7 workload, but the company also pays for idle capacity and engineering time to manage the hosts.
Operations
High. The team manages ECS and the underlying EC2 instances, including capacity, patching and recovery.
Reliability
99.9% availability is possible, but enough EC2 capacity must be available across failures and traffic increases.
Security
The team is responsible for securing and patching the EC2 hosts in addition to securing the containers and AWS configuration.
Implementation
not hard because the company already uses ECS, but EC2 capacity and scaling must be configured and maintained correctly.
Assumptions
The two engineers can manage EC2 hosts and Auto Scaling. The workload is steady enough for EC2 capacity to remain well utilized.
Risks
Poor capacity planning could cause unused capacity or not enough capacity during peaks. Host management could create additional operational work for the small team.
Tradeoff Rationale
This option fits the steady 24/7 workload and gives full host control for the nightly worker. It may also be cost-efficient if the EC2 capacity stays well used. However, it creates more work for the two-engineer team because they must manage capacity, patching and host recovery. Keeping 99.9% availability during traffic peaks also requires careful capacity planning.

OPTION 2 · 955c7a26-d9a6-426d-bc81-4c5ac59091f1

ECS on Fargate for all workloads

Summary
Run both the API and nightly worker using ECS Fargate. AWS manages the underlying compute capacity.
Components
ECS runs the containers on Fargate. The API runs behind a load balancer and scales based on demand. Additional tasks can start during the two-hour weekday peak. The nightly worker also runs as a Fargate task.
Advantages
No EC2 hosts to manage or patch. Easier scaling when demand increases. Lower operational work for the two-engineer team.
Disadvantages
The steady 24/7 workload may cost more than well-used EC2 capacity. Fargate provides less control over the underlying hosts. The nightly worker may not support its required special host setup.
Cost
Infrastructure management cost is lower, but compute cost may be higher for the twelve tasks that run continuously.
Operations
Low. AWS manages the underlying compute infrastructure.
Reliability
Easier capacity management can reduce operational risk. The ECS service can run tasks across multiple Availability Zones.
Security
The team does not need to patch or manage EC2 hosts. Container, IAM and network security are still the team's responsibility.
Implementation
Low to medium. The API should be easier to move, but the nightly worker must first be tested for Fargate compatibility.
Assumptions
The nightly worker can run without direct control of the underlying host.
Risks
The nightly worker may not work on Fargate because it needs a special host configuration. Fargate may also cost more for the steady workload
Tradeoff Rationale
This option reduces infrastructure management and makes scaling easier when demand doubles. This is a good fit for a small team of two engineers and can help support 99.9% availability. However, the nightly worker needs a special host setup, which may not be supported by Fargate. Fargate may also cost more for the twelve tasks that run continuously.

My recommendation

Selected Option
ECS on EC2 for all workloads
Option Id
268c42ca-938e-4338-af85-d1eb58c2e269
Decision
Run the API and nightly worker on ECS with EC2. Use Auto Scaling to provide enough capacity during the weekday peak, and keep the special host configuration required by the nightly worker.
Why
The workload is mostly steady, with twelve tasks running all the time, so EC2 capacity can stay well used. EC2 also gives the team the host control required by the nightly worker. Auto Scaling can add capacity when demand doubles.
Alternatives
Fargate would reduce host management and make scaling easier, but the nightly worker needs a special host setup. We do not yet know if Fargate can support that requirement. Moving every workload to Fargate would therefore create unnecessary technical risk.
Risks
The two-engineer team will still need to manage EC2 capacity, patching and host recovery. Poor capacity planning could also create idle cost or reduce available capacity during traffic peaks.
Assumptions
We assume the twelve continuous tasks keep EC2 capacity reasonably utilized. We also assume the nightly worker really requires host-level control and that Auto Scaling can provide enough capacity for the weekday peak.

Why not something simpler?

The simpler option is to run everything on Fargate. It would reduce management and make scaling easier, but the nightly worker needs a special host setup. We therefore accept the extra EC2 management because we need host control and 99.9% availability.

ADR working draft

Title
ECS on EC2 for API and nightly worker
Context
The service runs twelve ECS tasks continuously, demand doubles for two hours each weekday, and the nightly worker needs a special host setup. The platform team has two engineers and must maintain 99.9% availability.
Decision
Run the workloads on ECS with EC2. Use an Auto Scaling Group across multiple Availability Zones for the API, and keep the nightly worker on EC2 with its required host configuration.
Alternatives
ECS on Fargate for all workloads was considered because it would reduce host management and make scaling easier. It was not selected because the nightly worker may require host control that Fargate cannot provide.
Consequences
The team keeps full host control and can support the special worker requirement. The trade-off is more operational work for EC2 capacity, patching, scaling and recovery.
Risks
The main risks are higher operational effort for the two-engineer team, poor capacity planning during traffic peaks, and higher cost if EC2 capacity is underused.

Communicating the decision

Engineer
We will run the API on ECS with EC2 across two Availability Zones. An Auto Scaling Group provides extra capacity when demand increases. The nightly worker stays on a special EC2 host because it needs host-level configuration. The main operational work is patching, scaling, monitoring and recovery.
Cto
This design keeps the special worker requirement while supporting 99.9% availability. It gives us more control than Fargate, but it also creates more operational work for a small team. We should review the decision if the worker can later run without special host access.
Cfo
EC2 can be cost-efficient because most of the workload runs continuously. However, the real monthly cost must include idle capacity, extra resilience capacity and engineering time, not only compute prices. We should validate the full-month cost before final approval.
Ceo
The design is meant to keep the service available as the business grows and traffic increases. It also supports the special nightly workload without forcing a risky platform change. The trade-off is more infrastructure management for the engineering team.
Analogy
Think of EC2 like owning and managing your own building. You have more control and can customize it for special needs, but you are also responsible for maintenance. Fargate is more like renting a managed space: easier to operate, but with less control over the building.
Without Service Names
User traffic is distributed across application containers running in two separate locations for resilience. The system can add more server capacity when demand increases. A separate nightly workload runs on a specially configured server because it has different technical needs from the main API.

Final decision

I keep the ECS on EC2 recommendation because the nightly worker still needs special host control. After review, I would not approve production until we validate the real operational effort and full monthly cost. If the worker works well on Fargate or EC2 becomes much more expensive, I would review the decision.

Lessons learned

I learned that a recommendation is not enough by itself. I also need to explain how the decision will work in practice, what evidence will prove it, what success looks like, and what would make me change the decision.
